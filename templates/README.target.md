# Webhook delivery contract

Generated by the `webhook-contract` plugin. This folder makes your webhook
handler testable against how providers REALLY deliver events: duplicates,
retries, lost responses and out-of-order arrivals. Everything here is offline
and synthetic; no server, no network, no real provider data.

## Files

- `webhook-contract.json` - the delivery contract: event types, ordering keys,
  side effects and the idempotency boundary of each. You edit this.
- `fixtures/` - generated synthetic deliveries (do not edit; regenerate).
- `test_replay.py` / `test_replay.mjs` - replay harnesses (generated; do not
  edit, but only the ones for your language are needed).
- `replay_hooks.py` / `replay_hooks.mjs` - the adapter between the harness and
  your real handler. You edit exactly one of these.

## Workflow

In the commands below, `<webcontract.py>` is the full path to the plugin's
`scripts/webcontract.py` - the `init` run that created this folder printed it.
Use `python` instead of `python3` on Windows.

1. Edit `webhook-contract.json`: one entry per event type you receive, with
   every side effect and what makes repeating it safe (its guard).
2. Generate fixtures (deterministic - same contract, same fixtures):

       python3 <webcontract.py> gen --dir .

3. Validate contract + fixtures (structure, invariants, data hygiene):

       python3 <webcontract.py> check --dir .

4. Wire `replay_hooks.py` (or `.mjs`) to your real handler and side-effect
   layer, then replay:

       python3 test_replay.py         # Python handlers (unittest; pytest works too)
       node --test test_replay.mjs    # Node handlers (built-in test runner)

Failures are the point: they show exactly which side effect is not idempotent,
which ordering assumption is wrong, or which status code makes a provider keep
retrying.
